# Phase 2 — Test Application End-to-End

Tenant admins can now create two kinds of applications:

- **`production`** — validated by `domain`, exactly as before. Globally unique
  per active row.
- **`test`** — pinned to `localhost` and bound to a specific `port`. Unique per
  tenant per active row.

## Data model

`applications` now carries:

- `kind` — `application_kind` enum: `production` | `test`. Defaults to
  `production`.
- `port` — nullable `integer`. Required for `kind = 'test'`, must be null for
  `kind = 'production'`.

Constraints:

- `applications_kind_port_domain_check` — CHECK constraint enforcing
  `(kind='test' AND port IS NOT NULL AND domain='localhost')` OR
  `(kind='production' AND port IS NULL)`.
- `applications_production_domain_unique` — partial unique index on `domain`
  where `kind='production' AND deleted_at IS NULL`.
- `applications_test_port_unique` — partial unique index on
  `(organization_id, port)` where `kind='test' AND deleted_at IS NULL`. Two
  test apps in the same tenant cannot share a port; soft-delete frees the
  port.

The previous global `UNIQUE(domain)` is removed — many tenants can have
`domain='localhost'` test apps.

> ⚠️ Migration SQL is generated by `bun run db:generate` (manual). Apply with
> `bun run db:migrate` before running the API against an existing database.

## API contract

`POST /applications` accepts a Zod discriminated union on `kind`:

```ts
// production
{ kind?: "production", name, domain, description?, settings? }
// test
{ kind: "test", name, port (1..65535), description?, settings? }
```

The schema's transform forces `domain = "localhost"` on test payloads and
`port = null` on production payloads — the route handler always receives a
fully-normalized object.

`PATCH /applications/:id` rejects both `kind` and `port` (`.strict()`). These
are immutable after create — flipping kind would require a different
allowed-origin model and revoking API keys.

### 409 responses

The route surface discriminates conflicts so the admin can render
kind-specific toasts:

- `{ error: "DOMAIN_TAKEN", message }` — production unique violation on
  `domain`.
- `{ error: "PORT_TAKEN", message, port, conflictingAppName }` — test unique
  violation. The service runs a fallback `SELECT` against the active test app
  with the same `(organizationId, port)` so the conflicting app's name flows
  back to the UI.

Unique-violation detection runs through `isUniqueViolation`, which unwraps
DrizzleQueryError `cause` and checks the Postgres `23505` code. Anything else
re-throws so we don't swallow unrelated errors.

## Admin UI

The Create Application dialog now starts with a **kind toggle** (Production /
Test). Swapping the toggle:

- Hides the field that doesn't apply and clears its value.
- For test, shows a `Port` input with a `localhost:<port>` read-only preview
  and a small info tooltip explaining the per-tenant port pinning rule.

`ApplicationPortConflictError` is a new client-side error parallel to
`ApplicationDomainConflictError`. `ApplicationsPage` renders a distinct
sonner toast for each, and the `PORT_TAKEN` toast names the conflicting app
so the user immediately knows which existing app holds that port.
